# T22 受保护收件箱 v1：显式加密收件增量

对应 [#23](https://github.com/destinyTaoTao/evernook/issues/23)，实现为 `evernook.protected`。安装 `.[vault]`，固定 PyNaCl 1.6.2；默认普通运行时不导入、不启用此模块。初始化只供可信本地操作端使用，不是 MCP 工具。

```python
from pathlib import Path
from evernook import MemoryRuntime
from evernook.protected import initialize_protected_inbox, ProtectedInbox

# 路径均为占位；password 只能来自可信本地隐藏输入，不使用 argv/env/chat。
runtime = MemoryRuntime(Path("E:/configured-memory/runtime.json"))
access = runtime.access_from_file(Path("E:/configured-memory/mcp-access-owner.json"))
inbox = initialize_protected_inbox(runtime, Path("E:/configured-protected-inbox"),
                                 Path("E:/configured-vault-material"), password)
result = inbox.submit(access, source_bound_event)
assert result.state == "protected_linked"
assert result.encrypted_original_saved
assert result.message is not None and not result.message.original_saved
```

收件目录、密钥材料目录和普通运行目录必须是三个分离的仓库外私有目录；初始化拒绝已有目录。接收公钥、发送签名公钥及固定格式生成 key ID；Ed25519 私密签名材料可供写入端使用，接收私钥只以 Argon2id interactive 派生密钥及 SecretBox 加密保存。收件端加载公钥/签名材料，不加载或解密 recovery.json。公钥加密使用成熟 [SealedBox API](https://pynacl.readthedocs.io/en/latest/public/)，签名另行绑定发送者及对象；[口令派生](https://pynacl.readthedocs.io/en/latest/password_hashing/)不自行设计算法。

## 来源、事务与回执

1. `stage(access,event)` 验证核心身份和来源，检查 UTF-8/字段/1 MiB 正文上限，使用独立域的 HMAC 指纹进行幂等；没有公开低熵明文散列。原始 Event 加密，密文及签名绑定 inbox/object/key/version、脱敏投影、来源及指纹。独立 SQLite FULL/WAL 事务提交后只返回 `protected_pending_link`，消息回执为空。
2. `reconcile(access,object_id)` 核验固定接收材料、签名和对象绑定；将投影与受保护引用写入普通账本的同一事务，复用原有来源唯一性和任务生成。普通 `Receipt` 的 `original_saved=false,representation=projection` 保持原意；不能拿它声称明文已经进入普通账本。
3. 核心提交后才更新收件箱为 `protected_linked`。只有外层 `encrypted_original_saved=true,state=protected_linked` 表示两个存储已关联；这是密文保存确认，不授予解密/交付权限。状态读取重新核对核心引用，关联缺失时拒绝伪造成功，显式 reconcile 可修复缺失的引用。

两个库不伪装成跨库原子事务。任何窗口中断后，使用 `pending()`（每页最多100，按完成移除）和稳定 object ID 重试；核心已提交但最终确认缺失时仍可重试，不重复创建消息。改变原始内容但复用来源返回 `source_conflict`；更正/抑制不删除密文或自动恢复旧可见状态。

Core 0.1.46 起，`reconcile` 从读取密文、提交账本关联到最终收件箱确认均持有共享所有权栅栏；进入栅栏后再次校验调用端及 capture 权限。独占切换必须等待整次关联完成，等待期间发生切换或权限移除的旧调用不能继续。两库依旧不是单事务，进程崩溃仍可能留下 pending，必须按稳定 ID 恢复。栅栏不会自动发现未声明的独立收件箱，真实锁屏和旧保险库迁移门禁保持原状。

Core 0.1.55 起，`stage` 先持久登记，再持有与可信配对权限变更相同的核心写锁，锁内重新验证 capture 身份并提交收件箱密文；`reconcile` 同样在关联账本提交的写锁内重新验证。权限撤销先取得锁时，后续提交拒绝；收件先取得锁时，权限变更等待本次提交。登记可能在撤权后留下空登记，跨库失败仍可能留下待恢复的 pending，不能视为原子跨库事务。此顺序只覆盖遵循配对写锁的权限更改，不涵盖绕过接口直接修改身份文件或 OS 锁屏。

[--limit 1..100] [--after <cursor>]` 分页查看已登记 ID 和公钥标识；两者不是模型工具，列表不包含路径，也不是磁盘发现结果。登记前或登记写入失败时不提交密文，调用方必须保留输入并重试；登记成功后、密文写入前若崩溃，可能留下登记但没有对象，此时无绑定切换仍拒绝，只有绑定并核验相同空收件箱才可切换。登记不自动删除，密钥丢失、未知收件箱、多收件箱迁移与完整备份恢复仍需后续专门流程。

普通归档恢复控制重放及发布会核对已知登记：旧快照缺少当前登记时拒绝恢复，新的普通快照只保留非秘密的登记标识，不包含保险库密文或恢复密钥。无法连接原账本的异机恢复不能据此发现备份之后或从未登记的收件箱。

普通账本只保存 `[PROTECTED:ENCRYPTED_ORIGINAL]`、非敏感来源元数据、受保护引用及 HMAC。普通读取/词法索引拿不到原件；该模块没有解密方法或普通模型取密工具。初始化或加密失败明确报错，禁止回退明文；未完成初始化的目录不会被自动当作有效保险库。

## 显式加密备份（Core 0.1.75）

服务启动并绑定一个收件箱后，可信管理员可使用独立的备份接收材料创建新包：

```powershell
evernook service-protected-backup --config <runtime.json> --access <admin-access.json> --destination <new-backup-dir> --backup-keys <separate-backup-key-dir>
```

Python 可调用 `ServiceClient.protected_backup(access, destination, backup_keys)`；该操作不作为 MCP 模型工具提供。备份密钥目录可由 `backup-init` 初始化，必须和运行库、保险库及保险库密钥目录分离。备份恢复材料应另行保存；此操作不读取保险库口令或备份恢复口令，也不会验证它们。已取消的 SDK 请求不会发出；进行中的任务在安全检查点取消，不保证阻塞系统 I/O 被即时中断。

服务持有独占所有权栅栏和两个数据库写锁，校验单个已登记收件箱、所有密文签名、普通投影及双向关联；有 pending、未登记或额外收件箱、孤儿投影、无效签名或不匹配的密钥材料时拒绝。独立包以既有接收公钥加密、签名及认证的流式格式封装收件箱快照、加密恢复文件、写入材料和账本/关联绑定；快照执行 SQLite `quick_check`。包头暴露备份标识、备份密钥标识和密文长度等元数据，不含正文或明文写入密钥。绑定只覆盖不可变受保护关联；之后普通账本的抑制和更正仍须以恢复时选定的普通备份为准。

结果 `verification=signature_and_links_only`、`recovery_tested=false`：文件结构有效不等于恢复口令正确、能解密每条原文或异机恢复已经完成。未知、从未登记的其他收件箱不能自动发现。备份期间其他同账本写入等待；120 秒为协作预算，阻塞系统 I/O 可能超时。创建只写新目的地；中断后若目的地已出现，结果可能已提交，应核对后再决定，不自动覆盖。受控私有临时目录在强杀后可能残留，不承诺安全擦除。完整异机恢复、物理锁屏和日用准入仍需进一步验收。

验证使用隔离合成数据：源码备份 12 项及新增未配置服务拒绝 1 项通过，旧迁移证明与过期检查 2 项通过；非 editable wheel 的备份与旧迁移兼容共 14 项通过，strict mypy 通过。验证覆盖密文及独立口令、权限、取消、并发、篡改、损坏恢复材料、崩溃前后发布和普通抑制后的关联稳定性；没有操作用户保险库，也没有通过产品流程验证异机恢复。

### 离线验证暂存

在已恢复普通账本经显式缺失保险库模式激活一次后，停止服务；可信本地管理员可以使用 `backup-vault-stage --config <runtime.json> --access <admin-access.json> --source <vault-backup-dir> --destination <new-container-dir> --recovery-file <backup-recovery-file>`，交互输入备份恢复口令和保险库口令。SDK 的 `vault_restore.restore_stage` 仅供可信本地进程使用。运行时持有服务锁和账本独占栅栏，验证备份签名、加密流、保险库口令、对象和恢复账本关联，并发布全新的私有暂存容器。账本与备份的受保护关联不一致时拒绝；普通账本当前抑制状态不会被覆盖。取消与超时在分块处理时协作检查，阻塞的系统 I/O 仍无法立即中断。

**暂存不是接回，也不是日用准入。** 输出的 `attached=false`、`daily_admitted=false`；缺失保险库保护仍有效，未来接回时必须重新验证。发布后若响应或清理失败，可能报告 `vault_restore_outcome_unknown`；中断后目标目录也可能已出现，须视为结果不确定，不能直接覆盖或视为可接回。执行期间会在目标目录的父目录建立 `.evernook-vault-restore-*` 私有临时目录，包含普通记忆副本、账本密钥和保险库材料。正常退出会删除临时目录，但强杀或崩溃后可能残留；新版本的登记与清理范围见下文。本机保险库销毁尚未验证能发现或覆盖所有临时目录及另存备份，不能据此承诺彻底销毁。

Core 0.1.76（#214）使用隔离合成账本验证了恢复暂存、口令错误、篡改、未授权、运行中服务、账本不匹配、取消、发布故障和真实子进程发布前后崩溃；源码回归及 strict mypy 通过，非 editable wheel 的暂存 10 项和普通备份兼容 2 项通过。独立审查提出的分块取消与发布后结果不确定问题已补回归。未使用真实用户数据，未完成服务接回或日用验收。

### 暂存保险库接回

服务停止后，可信本地管理员可执行 `backup-vault-attach --config <runtime.json> --access <admin-access.json> --container <staged-container>` 并交互输入保险库口令；SDK 可调用 `vault_attach.attach`。接回时重新核验当前普通账本与保险库全部受保护关联和原文，然后通过单一数据库事务提交经账本密钥认证的路径和密钥材料绑定。相同容器可重试；提交结果不确定时重新执行相同操作核对，不要自行替换状态文件。

随后服务必须显式以该容器的 `inbox` 与 `keys` 目录启动。服务启动校验密钥材料及两库关联；旧保险库快照缺少普通账本已有对象时拒绝启动，合法的 pending 写入保留重试恢复。启动检查有 120 秒协作时限，没有宣称任意规模下可按时启动。恢复时旧客户端身份不会自动复用：需要由可信管理员将新客户端重新配对到原来源入口，才能按现有权限和本地口令查看该入口的私密内容。普通抑制状态不因接回被撤销，日用准入仍未开放。接回过程的 `.evernook-vault-attach-*` 私有临时目录也可能在强杀后残留普通账本副本及密钥，纳入 [#216](https://github.com/destinyTaoTao/evernook/issues/216) 跟踪；不能声称本机销毁覆盖它们。

Core 0.1.77（#215）在隔离合成数据上通过源码关联、崩溃、旧迁移与缺失保险库回归及 strict mypy；非 editable wheel 的接回 7 项、重配后本地显示请求使用合成接收器 1 项、备份后新增抑制仍生效 1 项通过。检查包含旧保险库快照回退、两个 pending 阶段、事务提交前后进程退出、绑定篡改以及再次普通备份恢复。首轮集成测试使用错误的清点结果字段，修正断言后复测通过。独立安全审查提出的旧快照及 pending 恢复问题已补检查与回归；未测真实用户数据、实际窗口与异机设备或大规模启动性能。

### 恢复工作区清理

Core 0.1.78 起，新建的恢复和接回工作区在写入敏感副本前，以账本密钥认证登记路径和目录身份。服务停止后，可信本地管理员可使用 `backup-vault-workspaces --config <runtime.json> --access <admin-access.json>` 查看登记；`backup-vault-workspace-clean --config <runtime.json> --access <admin-access.json> --id <登记编号>` 经本地交互确认后清理指定工作区。SDK 可调用 `vault_workspace.list_workspaces` 和 `cleanup_workspaces`。清理要求服务锁、管理员权限、有效登记、匹配目录身份、私有 ACL 和限定内容；拒绝重解析点及未知内容，并以锁定的 Windows 句柄删除对象。部分失败后应重新清点，不能把失败当作已销毁。

登记路径不存在时可能是被移动，或清理完成但登记更新前中断：系统保留登记并报告 `vault_workspace_missing`，需要人工核对。认证登记表与存在标记中任一单独缺失会拒绝继续；首次登记在两次写入之间中断也会留下需要人工处理的单标记状态。两个文件同时丢失或登记表回滚到旧的有效版本无法检测。旧版本在登记机制之前产生的工作区无法可靠自动发现或归属；已发布的保险库、用户另存备份及其他设备副本不在此清理范围。本功能仅删除经过验证的文件链接，不保证 SSD、系统快照、交换文件等介质内容被物理擦除；尚未与完整本机紧急销毁机制集成，日用门禁不变。

验证使用隔离合成数据：源码工作区与恢复／接回回归 15 项、后补定向测试和 strict mypy 通过；非 editable wheel 上工作区和恢复／接回回归 17 项，以及真实子进程在恢复与接回崩溃后按登记清理的 2 项通过。测试覆盖未经登记目录、目录替换、Windows junction、未知内容、损坏或缺失登记、服务运行中拒绝、目录句柄阻止重命名，以及清理后登记写入失败。测试未操作真实用户保险库，也未验证断电持久性、物理擦除或紧急销毁。

## CLI 与未启用范围

- `vault-init --config ... --access ... --inbox-dir ... --key-dir ...`：本地 TTY 隐藏输入并二次确认口令；管道、参数或环境变量不能提供口令。
- `vault-receive` 使用同样的四个路径选项，UTF-8 stdin 接受完整 Event；只输出脱敏回执。此 stdin 传输是可信本地采集接口，不是主口令输入途径。
- `vault-pending` 列出本入口的待关联对象，`vault-reconcile --object-id ...` 显式补齐关联。普通 CLI 不新增读取明文命令。
- `vault-inventory --config ... --access ... --inbox-dir ... --key-dir ... [--limit 1..100] [--after <cursor>]`：切换前由管理员明确指定一个收件箱，逐页检查 pending 与 linked 对象。Python 可调用 `ProtectedInbox.inventory(access, limit=100, after=None)`；返回已验证对象的脱敏回执和下一页 cursor。只校验信封签名、绑定及 linked 账本引用，不载入口令或解密；任一页对象或关联损坏时整页失败。普通身份不可清点其他入口。返回前重新核对管理员权限。
- Core 0.1.69 提供 `vault-verify --config ... --access ... --inbox-dir ... --key-dir ... ### 显式服务端加密收件

可信本地操作者可在首次服务激活前创建空收件箱与密钥目录，并在启动服务时同时指定 `--protected-inbox <inbox-dir> --protected-keys <key-dir>`。两项必须同时配置，不能用于旧共享模式；绑定身份或文件无效时服务拒绝启动。首次激活在独占切换栅栏内拒绝该收件箱中任何旧对象，旧原件与 pending 的完整迁移仍由 #115 处理。重启服务时须再次提供这两个路径；遗漏时私密收件明确拒绝，不回退到普通写入。账本外仍可能有未指定的独立收件箱，不能据此认定全局迁移安全。

可信本地调用方可使用 `ServiceClient.protected_receive(access, event)` 或 `service-protected-receive --config ... --access ...`（完整 Event JSON 通过 UTF-8 stdin），Event 必须 `sensitive=true` 且 `completion=complete`，来源入口须匹配已配对的 capture 身份。仅正文加密，来源等元数据仍可见，调用方必须使用不含私密正文的来源标识；未配置、权限不足、非完整事件、加密或存储失败均不明文回退。普通读取、搜索与维护只接触投影；此操作不是 MCP 模型工具，也不授予解密或披露权限。中断或响应丢失不证明未提交，应以同一来源与相同事件重试以恢复回执。
