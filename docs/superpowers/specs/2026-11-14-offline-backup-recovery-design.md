# Offline backup recovery

This design implements the user's decision for #117: when the original machine is gone, separately held encrypted ordinary backups and recovery material can be used on a new machine; one explicit trusted confirmation may reopen the whole ordinary snapshot. The restore must preserve every control recorded in that snapshot. It cannot know about corrections or deletions after the snapshot and must say so before confirmation and in the resulting receipt. The ordinary backup is not a vault backup.

## Authority and boundaries

The recovery password is entered only in a trusted local terminal, never through MCP, service RPC, model tools, argv, environment, logs or the browser. The existing `restore_backup` remains review-only. A new separate operation verifies the signed encrypted package and recovery material before showing a bounded review summary. A distinct explicit interactive confirmation is required to publish a normal runtime. A trusted Python API must require an explicit, narrowly typed acknowledgement and state that the caller is responsible for establishing real user consent; a model-provided boolean is not consent.

The package signature, every encrypted file's authentication, the archived SQLite integrity and foreign keys, archive manifest HMAC, and the archive's ledger identity must all agree with the decrypted key. Reject missing or incompatible material rather than falling back. Revalidate the same authenticated package at publication so a replaced backup or changed target cannot reuse an earlier approval. No original live runtime is required.

Publish only into a new private directory by staging, fsync and atomic rename. Never copy old `client.json` identities into the restored runtime: retain only the ledger fingerprint key needed to verify historical receipts, generate a fresh owner token and pair other clients anew. Provide the owner access file through a private file, not plaintext CLI output. A durable authenticated receipt binds the source backup, chosen destination and fresh identity; retry after a lost response must not create a second identity or overwrite changed data. Define and test before/after-rename crash behavior. Plaintext staging can remain after forced termination and is not secure-erased; document this and ensure it is private.

The backup's original records, visibility controls, versions, history and evidence remain intact. Do not assume backed-up approvals authorize new clients, replay pending external actions, silently start maintenance, or turn an old model admission into new-device admission. Determine how pending workflows and restored service activation are handled before exposing the operation. A restoration receipt must disclose source backup identity/time, that later changes are unknown, and that restored data may be stale. Independent copies and the old machine are not synchronized or erased.

## Protected data

Ordinary backup v1 does not contain encrypted inbox objects or vault recovery material. Registry entries and ordinary encrypted projections may exist in its ledger: never call those restored secrets, remove them silently, or treat the missing vault as proof of deletion. A protected backup/restore path must separately authenticate the chosen inbox and recovery materials, preserve associations and keep the vault locked on the new machine; user-selected exclusion must be explicit. The ordinary runtime should remain usable when the protected asset is unavailable, but the service currently refuses activation when protected links exist. That behavior needs a separately reviewed safe missing-vault state rather than bypassing its guard. Multi-inbox, incomplete/pending objects and unknown inboxes require explicit handling and cannot be claimed complete by the single-inbox migration proof.

## Verification

Use only newly generated synthetic stores. Cover wrong/missing recovery material, package/file tampering, cross-package swaps, mismatched ledger/key and partial output; snapshot controls, original evidence, old-token rejection and fresh-owner access; confirmation cancellation and package mutation during approval; before/after-rename process crashes and retry; an independent process reopening the destination after the original runtime is unavailable; restored service and protected-registry interactions. Verify no secret/password/old token reaches API/CLI output or logs. Do not weaken existing backup review, cutover or daily-use tests. Actual backup files, physical device loss and physical identity are not inferred from these tests.
