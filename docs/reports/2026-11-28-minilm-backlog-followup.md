# 百万库的待索引来源选择与后台恢复

## 第一条来源

原账本保留了上次 120 对混合读写的 120 份回执。按回执 ID 回读原文、来源、内容版本、可见状态和当前分块，120 条均未获得当前空间的 MiniLM 向量，其中 4 条已有词法索引。原文与回执的有序 SHA-256 为 `9e61db0f798935d3715caad1126b9102f2d5c2870bf460f59f449c2cb0a11c67`。

| Windows 实测 | 结果 |
| --- | ---: |
| 0.1.99 原账本旧选择 SQL，限一条，推理前中断 | 5.001 秒 |
| 0.1.100 从原账本副本重新核对覆盖并发布 | 56.505 秒 |
| 最终写事务，从 BEGIN IMMEDIATE 到开始执行 COMMIT | 0.232 秒 |
| 核对后，按原顺序选取第一条 | 1.497 毫秒 |
| 正式 refresh，限一条、5 秒预算，含真实模型与提交 | 1.630 秒 |

旧查询在返回首条之前逐一检查已有百万文档及其分块。原账本已有检查点，但服务按需建表后，数据库的 schema 版本从 127 变为 135。仅检查当前触发器定义不足以证明过去的每次变动都被记录。后台对显式启用且结构匹配的旧检查点执行一次权威核对，在读快照中暂存差异，发布前复核并发写入、前台活动和权限。前台写入改变数据版本时放弃本次结果，下一轮可重试。新选择查询用未覆盖来源的稀疏索引和发生变动的来源 ID 构成候选，按原接收时间及 ID 确定顺序，回源核验资格、版本和已有分块。前台读取的 100 项差异核对上限保持原值。

在保留原账本的独立副本上测试。一次旧版维护用于观察调度耗时，语义仍有 120 条积压。随后安装 0.1.100，使用原 MiniLM 配置和正式维护身份。首条返回的 ID 与旧负载第 0 轮的写入回执相同，提交后全库 1,000,001 个向量、119 条语义积压。该样本仅计一次选择与刷新。wheel SHA-256 为 `c7a6720e5dd44f0b7bceea04f757ba569b799ec95a2720b8f378484b9f967704`，117 个 Python/JS 模块与代码逐文件核对。安装包的语义检查点与服务维护回归共 19 项通过。
