# 2026-11-15 架构与恢复安全复核

## 结论与范围

审查基线为 `d817be9...7b6510a` 的五个提交，并沿调用链核对既有备份、初始化、服务启动、控制重放与验收记录。当前分支为 `codex/vault-recovery-243-237`；未切换日常运行库，未操作用户保险库。工作区原有的 CONTEXT、requirements、两份 ADR 和 11-01 评审文档均保留，不纳入本轮提交。

本地单用户、SQLite 原始证据账本、可重建派生记忆、独立服务和保险库分离的方向仍符合已确认目标。没有证据支持为了本轮问题引入分布式服务、图数据库或新的框架。主要缺陷是跨文件/数据库生命周期不完整，以及验收只检查中间文件而未重启剩余服务，不能用“已有 API/测试通过”推导“所有非人工工作都完成”。

GLM 已实现多库暂存接回、认证绑定、出生私有 NTFS 创建和销毁主干，但下述七项实现/覆盖问题足以否定原先“合成层面已无已知未实现项”的结论。修复保留原始证据、普通投影和历史关联，没有开启日用或模型准入。

## Standards

1. **P1，初始化提前释放生命周期句柄。** 原 `protected._initialize_protected_inbox` 在 SQLite 接管之前退出两个 PrivateTree，目录及预创建文件可被替换。回归在真正的 SQLite 入口尝试 rename 根、密钥目录、writer.key 和数据库：基线未拒绝，修复后拒绝。现在树和文件一直持有到建表、绑定核验及 ProtectedInbox 构造结束。
2. **P2，保险库备份仍走路径式创建。** 原单库使用未登记 TemporaryDirectory，多库仍使用旧 workspace 和 mkdir→icacls。现均改用注册的 secure_workspace，SQLite 目标先按句柄出生私有创建，密文写入已持有的输出流；发布复制到出生私有文件，逐文件核对摘要，最后写认证头。故障后可能保留私有部分目标，返回 `vault_backup_outcome_unknown`，不覆盖、不自动把它算成有效备份。备份格式不变。
3. **安全假设更正。** 目录句柄的 share mask 不能阻止按子路径创建文件；独立 NTFS 合成探针已验证，不能继续声称“持有目录就杜绝植入”。本轮修复曾在检查空根后提前注销，该中间方案已被独立评审否决并修正：只有根成功进入 delete-pending 后才持久化完成/注销，此时新增子文件确实被拒绝。保留未验证窗口的结果未知语义。

## Spec

1. **P1，多个注册恢复副本漏清理（#116/#216）。** 原遍历 entries 时又 remove，三个登记只清理两个却报成功。现在遍历副本，逐项按认证登记清理；回归含三份合成 recovery 材料副本。
2. **P1，绑定释放中断不可续跑（#116）。** 原先删除/改写绑定及配置，再提交账本；重试却先依赖旧绑定，尚未读取进度就被拒绝。现在先持久化 HMAC 保护的 v2 转换意图，记录精确前后文件和附件状态、目录身份、授权调用端和时间。重试先读取意图，仅接受记录中的前态/后态，幂等补完文件与账本，提交之后才标完成。未完成记录阻止服务及受保护操作重新开放。
3. **P1，正常多库降单库后不能启动（#116/#241）。** 原有两条登记和原件关联仍被当成两个活动库。现在增加认证销毁墓碑，活动集合排除已销毁库；保留原登记、投影和关联用于审计，旧副本不因此重新获得解密入口。控制检查点也包含墓碑，可信控制重放拒绝缺失/分叉墓碑。
4. **P1，恢复多库降单库丢失附件证明（#117/#237）。** 原 DROP 多库附件后保留 restored_missing_vault 配置，却不生成单库附件，正常完成也必定拒绝。现在转换对应的认证单库附件，保留恢复回执关系；已补恢复→接回→销毁一个→重启剩余单库服务→普通控制保持的合成端到端。
5. **P2，单库重启只核对路径（#241）。** 原未核对绑定的 inbox_id、key_id 和材料摘要。新回归在 recovery.json 加入换行，原服务仍可启动；现在明确拒绝 `protected_single_binding_mismatch`。正常收件不改变这些材料摘要。

旧 v1 销毁记录仅在原认证绑定仍能证明精确目标时迁移为 v2；旧绑定已部分释放则返回 `vault_destruction_legacy_recovery_required`，不能从不完整材料推造授权或自动忘记残留。

## 仍不能保证的部分

- **文件系统删除与进度文件不能原子提交。** delete-pending 成功、认证记录尚未持久化即退出，可能留下指向已缺失空根的登记。当前明确拒绝/报告 unknown；需要人工清点，不能把“目录不存在”当作已经证明销毁。旧版未登记副本、登记整体回滚/丢失也不能自动发现。
- **不是同 Windows 账户内的完整安全隔离。** 句柄、ACL、身份、签名和 HMAC 缩小具体替换/竞态窗口，不抵御已经控制账户、复制密钥或取得既交付明文的进程；unlink 不等于物理擦除。独立备份与其他设备不在本机销毁范围。
- **性能和学习目标没有因此达标。** #81/#84 的十万/百万规模及完整链路目标，#86 的模型资源门槛，#120/#148 的反思/答案质量与相关性，#143 的多面板/写入竞争实测仍开放。本轮不是新的性能测量，不继承旧版本的长跑或 p95 成绩。墓碑校验会增加活动集合核对；没有百万级墓碑/备份吞吐基准。
- **#116 的独立销毁凭据目标仍未实现。** 当前继续沿用 GLM 的“保险库口令 + 本地不可逆确认”，不能称已经交付独立销毁助记词。引入新凭据涉及保管、丢失恢复、已有库迁移及授权语义变化，需要用户确认并实际保管，不在审查修复中静默改变。
- #115 的真实锁屏/物理本人认证、真实浏览器私密记录流程，#117 的真实异机恢复，以及睡眠/重启和日常使用验收仍需用户参与。跨 Windows 版本和未登记旧资产清点也未完成。

规范轴：两项原实现问题和一项已纠正的安全假设；需求轴：五项确认缺陷。最严重的共同类别是敏感资产生命周期与跨介质状态转换。本轮没有理由宣称绝对安全、所有场景可自动恢复，或所有不需人工的项目工作都已完成。
