## 最小链路与确认语义

捕获入口是原生 `agent/request` waterfall：先等待已挂载 JSONL 后端的 `ctx.sessions.flush(session)`，再把会话头与事件提交到实验 SQLite 收件库，最后继续请求。原生 `followup`、内存 inbox 追加和 `session/event` 发布均不作为保存成功回执。

`agent/request` 发生在当前 `user/message` 正式加入请求历史之前；此时 flush 保全的是已持久化 inbox 中的用户原文。因此收件与重扫必须同时识别 inbox 插入，不能只监听 `user/message`。独立 SQLite 读连接在模型适配器真正开始派发时验证了原文已可读。

后续会话通过原生运行时上下文收到已采集证据，保留会话与事件 seq 引用，并标识不可信数据。没有将证据放进核心人设或系统指令。当前实验回放全部少量合成文本，不代表已经实现相关性检索、过滤、更正、遗忘或上下文预算。

`agent/turn-stopping` 收集已结束步骤的助手/工具记录；最终 `turn/end` 由显式 capture 或后续重扫取得。收件事件保持原始 JSON 语义，不按文本相同合并。重扫采用真实只读持久化句柄，拒绝同一来源的不同事件内容；所有事务成功后才记录提交水位。

## 能力与缺口矩阵

“支持”仅指该版本、该插件组合及列出的合成场景通过。

| 用户文本、标点、换行、emoji | 支持 | 模型派发前独立读连接可读；强杀后从宿主 inbox 补回 |
| 完成的助手文本、工具调用与结果 | 支持 | 真实 Agent Loop 与 ToolRuntime 执行，收件保留原始事件 |
| 来源与时间 | 支持 | 原始会话头、事件 seq/time、消息 ID/role/source；seq 不冒充全局消息 ID |

| 模型请求失败后重试 | 支持 | 2 次模型请求，仅 1 个用户消息事件；失败 attempt 与成功回复分别保留 |

## 故障验证与剩余工作

三种子进程强杀窗口为：宿主 flush 完成但 sink 尚未提交、sink 已提交但模型尚未开始、助手已输出部分流但尚未形成持久化消息。父进程收到目标 checkpoint 后终止子进程；重启真实 JSONL 后端并对全新收件库重扫两次，验证用户原文与来源、幂等和未闭合 turn。Windows 进程终止不代表断电恢复，也不证明所有硬件缓存与磁盘故障语义。

确认的原生缺口需要在 R1 契约前处理，最小建议为：

1. 在调用 `followup` 前建立稳定来源消息身份的耐崩溃收件与冲突检查；相同身份/内容返回原回执，不同内容拒绝。不能用文本相同去重不同真实交流。
2. 明确流式保证：若要求显示过的片段也能恢复，需要宿主在显示/确认之前持久化片段或独立可靠发件箱，并定义片段身份和完成范围。只重扫最终消息无法填补实测强杀缺口。
3. 记忆服务独立归档附件时，应复制并验证字节及恢复关系，不能将宿主文件引用称作原件已归档；不可检查附件也不能直接进入普通索引。
4. 固定实际目标桌面/CLI profile 并补验正常入口的捕获阶段、安装位置、用户提示和自动补齐。当前原型尚不能替换用户日常 dsh。

上述是待落实的兼容性方案，不是已经批准或实现的 R1 接口。仍需完成其他 R0 选型/凭证验证，并通过 T04（Issue #5）确认内核、平台、敏感分流、字符坐标、流式契约与恢复门槛。
