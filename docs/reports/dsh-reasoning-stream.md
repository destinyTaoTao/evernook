# dsh可靠工具流的有界推理兼容

2026-11-08，实施 [#99](https://github.com/destinyTaoTao/evernook/issues/99)，接续 #94/#92。目标仍为固定 dsh 0.2.1-rc.5、Node24.12.0、Python3.14.4、Windows本机独立宿主。

## 问题与边界

原 `durable_tools` 拒绝 reasoning。已安装目标 SDK 的 `ReasoningBlock` 与真实 `@deepseek-ai/dsh-llm-deepseek` Messages 适配器会产生独立 reasoning-delta，签名进入 finish.replayState；这使正常推理后调用工具的响应在已有发布屏障前中断。

本批仅扩充已有完整结构保存路径：接受顺序有界推理块，最终正文必须与增量拼接精确一致且Unicode完整。推理、文本与工具仍分别建模；推理在 system 结构证据及原始帧附件中保存，不混入权威答案文本流，不成为用户事实或执行授权。完整帧、推理文本和重放元数据取得真实 Core 完整回执，且答案流关闭成功后，才按原顺序发布推理/工具结构并允许工具执行。

推理不逐块实时发布。推理位于响应前面时，后续文本也因有序队列延迟到真实provider结束；这是显式可靠工具模式的当前延迟边界，默认模式不变。普通文本在结构块之前仍可先取得分块回执再显示。附件、未知结构、重叠非工具块继续拒绝；工具参数仍需完整有效JSON且调用ID唯一。

安全检查同时覆盖连续推理/答案文本，避免把 `pass` 与下一通道的 `word=...` 拆开规避。推理保存失败、敏感/超限、不闭合、内容不符、provider错误或取消，不发布推理/工具结构，不执行工具；既有安全文本前缀保持原恢复语义。不新增宿主补丁、模型、权限或外部服务。

## 验证结果

- 新增真实 SDK/Core 9项通过：拆分代理对、推理→文本→工具→结果→下一轮回答；完整帧逐字回取、输入关联及签名重放。执行工具前完整回执已存在，推理进入前队列无内容提前泄露；答案流不包含推理。
