## 迁移前的只读可行性原型

为让下一步可评审，另在外部 100k 合成快照上执行三个结构对照，**没有接入 Core 或迁移运行库**：

| 固定快照，仅 global semantic + keyword SQL | 后 30 次 p95 ms | 与当前 Core 的候选 ID |
|---|---:|---|
| 来源元数据投影，仍逐行连接原向量表 | 3423.40 | 31 次均一致 |
| 原生 vec0 独立向量结构 + 稳定 FTS 排序 | 624.53 | 31 次均一致 |
| 上项 + 边界同分完整读取、稳定 ID 排序的 FTS rank 流 | 357.47 | 31 次均一致 |

最后一项最多读取 142 个 rank 行，未用简单截前 100 丢掉同分来源。三个条件固定同一问题、全来源可召回、每来源一 chunk/一 FTS 行；重复 31 次不是 31 个质量场景。这些仅测两条 SQL 通道，排除了近期通道、覆盖状态、权限、融合、最终回源及 tokenizer/模型，**连原型自身也未达到 150 ms，不能声称整体达标或直接接入**。它们说明仅加缓存不够，方向还需要检索结构与实时一致性设计。

原型复用已安装并实测的 sqlite-vec 0.1.9，无依赖升级。参考作者的 [vec0 说明](https://alexgarcia.xyz/sqlite-vec/features/vec0.html)与 [KNN 说明](https://alexgarcia.xyz/sqlite-vec/features/knn.html)；在线文档展示的版本较新，构造及查询语法另在本机 0.1.9 实际验证。所有新表都只在隔离合成原型数据库，不代表热写、来源撤回、多 chunk、恢复或权限的一致性已实现。

## 资源证据勘误与复测

旧 `monitor.py` 使用 Toolhelp PID 父链；一次窗口峰值含 25 个进程，独立创建时间核对证实其中 21 个存活进程在实验前一天已经启动。PID 复用使历史父链错误地把它们算入实验。**本轮所有旧 PID 父链 private/working-set 峰值均归属未经验证，撤回资源验收用途**，不能仅因查询失败计数为零就恢复有效。原始文件保留，计数、向量、答案评分与时延观察不因该归属错误改写。外部 `resource-pid-reuse-proof.json` 只保留创建时间/归属证明，不发布无关应用名称。

新 `ExperimentJob` 用独立 Windows Job 能力启动包装器，包装器在创建目标前入 Job，关闭继承句柄；不允许 breakaway。查询实际 Job 列表（含嵌套 Job），打开进程句柄后再次验证成员身份，记录创建 FILETIME。停止只使用该 Job 和实际启动句柄，移除按 PID 父链执行的 taskkill。官方 [Job 进程列表](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_process_id_list)说明包含嵌套子 Job；实际 Core 内嵌套工作器、无关进程不受停止影响、PID 复用排除及预算退出均有真实进程回归。

## 合并前追加：tokenizer 取消异常传播

用户随后明确要求阶段提交、推送并合入 main。对 `590ad42` 启动全量契约诊断时，发现既有 tokenizer 的并发预热取消返回了 `tokenizer_unavailable`，而契约要求 `context_canceled`。单项首次通过，完整 tokenizer 模块复现失败；Future.result 插桩实际观察到预热关闭执行器后，主线程收到 CancelledError 或管道 OSError。这不是仅凭一次重跑通过就归为偶发失败。

scoped count 仍先回收进程/IO，再在此异常分支复核调用方取消标记；已取消返回 `context_canceled`，未取消保持 `tokenizer_unavailable`。新增确定性回归在 Future.result 前触发相同竞态，分别覆盖 Future 取消/管道错误、有/无调用方取消四种组合，并核验实际子进程退出。新增回归先两项 subTest 失败，修复后通过；完整 tokenizer 模块源码 12 项通过（8.601 秒），真实 Core-only wheel 安装版 12 项通过（8.729 秒），独立审查未确认新问题。Core 全部 96 源文件 mypy 及 tokenizer/测试两文件 strict 检查通过。

新 wheel 仍为本地阶段版本 0.1.97，SHA256 `c5d27603ecea54178560b2d13f65d0ac18a049815ae93af0626d8dd0e3ecb5df`，101 个源码成员与修复后源码逐字节相同。旧性能/质量窗口不重写成新 wheel 的测量。全仓 mypy 另被未改动的 test_topic_views/test_semantic 混合模块导入阻断，origin/main 同样存在该导入；不宣告全仓 mypy 通过。原始全量诊断与独立复测日志外置保留，最终长测结果及合入状态见 [PR #245](https://github.com/destinyTaoTao/evernook/pull/245)。本段不将发现失败的诊断运行改写成单次全量通过。

## 下一步需要确认的结构变更

在当前约束下，现有全扫描实现已经实测失守 1 秒/150 ms 门禁。下一步建议保留原门槛，新增**可回滚的派生索引 schema 与重建流程**，而非继续宣称现有结构可达标：

1. 将前台反复从 Event/Receipt JSON 计算的来源资格、状态/内容版本及覆盖水位保存为事务内维护的派生投影；提交、更正、抑制、删除、恢复重放都必须更新或使其失效。
2. 把向量候选查询与原文大表连接分离；原文仍在现有账本，选中证据继续回源核验，过期或无法证明覆盖时降级，不能把缺索引当作历史不存在。
3. 新派生结构可以全量重建，默认关闭；回滚关闭新读取路径并使用现有实现，不迁移/删除原始消息，不默认更换模型或新增服务。
4. 补版本/损坏/取消/恢复一致性回归，再执行两种规模、全部条件的冻结矩阵及质量/资源门禁。模型整体质量仍独立开放，不能由索引性能替代。

这涉及新的持久化结构和数据回填，不属于本轮已实现的无新表优化。按用户提供工程协作约定第 4 条，未明确授权的新数据迁移需要确认后实施。真实设备、日用体验、独立销毁凭据与先前恢复审查的残余边界仍保持开放；本轮不承诺物理安全或灾难恢复保证。
